# DDL maintainer reference

This page is for people and agents maintaining DDL, its adapters, and its documentation. For installation and everyday use, start with the [project README](../../README.md), [Codex guide](../../hosts/codex/README.md), or [Claude guide](../../hosts/claude/README.md).

## Installation reference

The environment installer runs the [generator](../../tools/build.py) first, then symlinks the nine skills (eight commands and `ddl-protocol`), the `explorer` and `worker` agents, and the gate hook from the generated layout under `dist/` into each selected host's home, and merges the adapter's settings fragment. Codex also receives the `rules/ddl.rules` link. Without host flags, the installer selects the host home directories that already exist; if neither exists, select `--claude` or `--codex` explicitly.

| Host | Merged file | DDL settings |
|---|---|---|
| Claude | `~/.claude/settings.json` | Gate hooks; spawn depth 1 and attribution off, which stay global settings for every project |
| Codex | `~/.codex/hooks.json` | Gate hooks; the push rule is installed separately |

Existing settings are retained. The first change to a settings file keeps a backup beside it as `settings.json.ddl-backup` or `hooks.json.ddl-backup`. The installer does not write Codex `config.toml`; to match SWARM's `max: 5`, set `[agents] max_concurrent_threads_per_session = 5` there yourself. Doctor reports a missing cap as optional.

The install, doctor, and uninstall scripts accept `--claude`, `--codex`, and `--dry-run`. Uninstall removes DDL-owned links and the merged fragment while leaving unrelated settings and files. Doctor also reports when `dist/` is older than its sources. The hook requires Python 3 and the standard library; if Python is absent, hook execution fails open and the protocol still applies as instructions.

### Updating a linked installation

Pull updates through Git in the DDL clone, then run the installer again: it rebuilds `dist/`, which the links point into, and refreshes the merged settings. For the catch-all matcher update, rerun installation even when the hook link already points at the clone. Review changed Codex hooks in `/hooks` before relying on them.

```bash
bash DDL/bin/install.sh
bash DDL/bin/doctor.sh
```

For project-contained layouts, use `bash DDL/bin/install.sh --project your-project` with an optional host flag. It builds, then copies `dist/claude/.claude/` into the project's `.claude/` or `dist/codex/` into the project's root, and keeps an existing instruction file. Repeat the project install to update the copied files. Claude trusts project hooks through folder trust; Codex requires project trust and hook trust.

## Source files and generated files

The sources are one host-neutral tree: `skills/`, `protocol/`, the four implementations in each `hosts/<host>/`, and `tools/ddl_gate.py`. The host-specific adapter files and the instruction-file templates live beside the implementations in `hosts/<host>/`. The [generator](../../tools/build.py) writes both deployable layouts into `dist/`, which is untracked:

| Source | Generated by `tools/build.py` into `dist/` |
|---|---|
| `skills/<name>/SKILL.md` (the eight commands, `/name` notation) | `dist/claude/.claude/skills/<name>/SKILL.md` byte for byte; `dist/codex/.agents/skills/<name>/SKILL.md` with `/name` turned into `$name`, plus `agents/openai.yaml` |
| `protocol/SKILL.md` (the entry) and `protocol/<operation>.md` (the six operations) | `skills/ddl-protocol/SKILL.md` and the six operations in each host's layout, with `{host}` and `{Host}` rendered to that host's name; the Codex entry also gets `agents/openai.yaml` |
| `hosts/<host>/{start,approval,parallel-work,git-review}.md` | Folded into that host's layout only: `start.md` becomes the `## Host` section of the entry, and the other three become the `## Implementation` section (`### Mapping`, `### Observed`, `### Coverage`) of the operation of the same name |
| `hosts/claude/guidance.md`, `settings.json`, `agents/` | `dist/claude/.claude/CLAUDE.md`, `settings.json`, `agents/` |
| `hosts/codex/guidance.md`, `hooks.json`, `config.toml`, `agents/`, `rules/` | `dist/codex/AGENTS.md` and `dist/codex/.codex/` |
| `tools/ddl_gate.py` | `dist/claude/.claude/hooks/ddl_gate.py` and `dist/codex/.codex/hooks/ddl_gate.py` |

Command bodies translate `/command` invocations to `$command` in the Codex form; the protocol entry and its operations are rendered, and the implementations are folded into them. Generated YAML prevents implicit invocation of the command skills; a command reads the entry in Phase 0 and one operation before each action it defines, each file carrying the host's implementation inside it. READMEs are never deployed.

The canonical behavior lives in the [shared protocol](../../protocol/SKILL.md), written as an instruction-set reference; command files refer to it rather than duplicating its rules. The entry `SKILL.md` holds Start, the Instruction set (ten directives, each with Syntax, Count, Placement, and Rule), Pending STOP, the Reading map, and Interruption. The Reading map has three columns, Operation, Read before, and Implementation, and routes to six operations flat beside the entry, each with the fixed sections Read when, Syntax, Operands, Operation, Formats, Example, Exceptions, and Implementation: [Approval](../../protocol/approval.md), [Parallel work](../../protocol/parallel-work.md), [Notebook](../../protocol/notebook.md), [Close](../../protocol/close.md), [Git review](../../protocol/git-review.md), and [Command authoring](../../protocol/command-authoring.md). Each Example holds one short worked example beside the rules; the complete command template is the Example of Command authoring. In the source, the Implementation column names its file through `{host}` placeholders; a generated Reading map row points at the `#implementation` fragment of its operation or at the entry's `#host` fragment, because an installed protocol folds its own host's four implementations into those files and has no `hosts/` directory. Those four, in [hosts/claude/](../../hosts/claude/) and [hosts/codex/](../../hosts/codex/), are `start.md` for the entry's Start and one for each operation with host-specific differences (`approval.md`, `parallel-work.md`, `git-review.md`), named after it; Close reads Git review's, and Notebook and Command authoring need only `start.md`, already read. They hold Read when, Mapping, Observed (Fact / Version / Date), and Coverage, refer to operations by name, and carry no links; tool names appear only in the implementations under `hosts/`. The Mapping of each `start.md` holds only Session start, Compaction, Notebook loading, Adapter paths, and the `+++DDL_PHASE` and `+++DDL_REPORT` markers; the lookup order and Phase 0 loading live in the commands' Phase 0 lines and the instruction files. No file under `hosts/claude/` or `hosts/codex/` is named `claude.md`, which Claude reads as a nested `CLAUDE.md` on a case-insensitive filesystem (observed 2026-11-02, Claude Code 2.1.316); the instruction-file template is `guidance.md` for that reason, and the generator renames it on output. These are files within the selected protocol skill, not extra user-invoked commands.

The source tree of the protocol and the implementations:


The generator renders the entry and the six operations into `dist/claude/.claude/skills/ddl-protocol/` and `dist/codex/.agents/skills/ddl-protocol/`, and folds only that host's four implementations into them: `start.md` as the entry's Host section, and the other three as the Implementation section of the operation of the same name. The other host's implementations are absent from an installed protocol, which has no `hosts/` directory. Each host guide shows the generated tree it receives.

### Project overrides and session context

A project's own command skill takes precedence over the environment-installed command. `commands/<name>.md` can add project facts such as target paths, protected terms, and validation commands. Commands use the project's protocol copy when present, otherwise the user-level copy under `~/.claude/skills/` or `~/.codex/skills/`; the commands' shared Phase 0 lines and the instruction files state this lookup, and links inside the protocol resolve relative to the selected copy, never to another installation.

Claude loads the instruction file and its `design.md` import at session start and after compaction. Codex loads `AGENTS.md`; trusted SessionStart hooks inject `design.md`, or the skill reads it when the hook is unavailable. A worker receives a self-contained prompt with its scope and approved work; it does not depend on inheriting the lead's conversation. The Operands, Operation, and Exceptions of [Parallel work](../../protocol/parallel-work.md) define worker roles, the spawn, and fallback behavior, and the host's implementation `hosts/<host>/parallel-work.md` ([Claude](../../hosts/claude/parallel-work.md), [Codex](../../hosts/codex/parallel-work.md)), folded into that operation's Implementation section on install, maps `type: Explore` and `type: general-purpose` to the host's agent definitions.

`design.md` contains the human-agreed Experience and any Binding Decisions, Direction, Acceptance Gates, principles, scopes, and validation the project needs. Automatic memory is a recall layer, not a source of binding agreement. The Operands of [Notebook](../../protocol/notebook.md) define section ownership and retirement rules, and its Formats define the literal strings commands write there, such as `passed <date>` and `Approved plan (<date>)`; a mark a command writes must be defined in those Formats.

## Batch approval

At a required STOP, present one concise overall recommendation and the complete current review set: visible numbered compatible actions with stable IDs, recommended resolutions, and their material impacts. Keep important risks and unknowns in that report and make detailed evidence separately accessible. A set containing several proposals still receives one native approval interaction by default.

Offer **Approve all current recommendations**, **Choose a subset or request changes**, and **Hold**. Explicit approve-all authorizes exactly the displayed ready set and recommended resolutions. It does not authorize undisplayed or future items, later STOPs, unconfirmed outward actions, or silent changes to Binding Decisions. Apply the approved set without follow-up approvals per file, item, or section.

Subset editing is optional and starts only when requested. Use native multi-select/checklist controls or one grouped form when the host supports them; never impose a typed ID list or an automatic N-item, N-turn approval loop. Use Claude's native `multiSelect` only when the exposed schema supports it. The observed Codex asynchronous function accepts only `questions`, `title`, and `options`; do not invent a `multiSelect` property for it. Offer compatible subsets as native choices when a grouped selector is unavailable.

The native question is the final interaction while waiting at that STOP. A synchronous question waits for the actual submitted answer. On an asynchronous host that keeps the question answerable after turn completion, end the turn after the request receipt and wait for that answer. Respect the tool's permitted purpose and mode; do not switch modes to bypass a restriction. A receipt, cancellation, dismissal, no selection, or timeout is not approval. An answer must authorize the current displayed set or an explicitly selected subset.

## Close stage

Work ends in a [Close](../../protocol/close.md) stage. `/realize` runs it after the last implementation stage, and `/commit` runs its scan before the Git review, following its Operation in order: reflect the code into `design.md`, audit the documentation the change set touches, align language pairs, validate, then prepare one Git review of the whole change set. Inside `/realize` the approved plan authorizes the Close edits, and the Git review is where the user sees them. Inside `/commit` the findings form one batch approval first. After the commit, the report states that nothing remains or names leftovers with reasons; no next command is suggested. `/reflect`, `/docs`, and `/resonate` remain standalone commands.

## Runtime boundaries

The catch-all matchers inspect tool calls dispatched through the host's hooks. While a report awaits human input, the gate permits exact known read tools, human-question tools, input-free polling where supported, and bounded literal shell reads. Unknown tools, worker follow-ups, general scripts, and unsupported shell forms are denied on covered paths. Use display forms such as `cat`, `head`, `tail`, `rg`, or `sed -n '1,10p' file` to clarify a report.

This is a static guardrail, not complete STOP enforcement or a sandbox for ambient executable and configuration behavior. Runtime paths outside the hooks, asynchronous transcript timing, and unexpected errors limit enforcement. General STOP errors fail open with a warning. The protocol's Approval operation still applies, and the agent judges whether a submitted answer approves the current report and scope. Ordinary commits and pushes also have the independent content review below.

Question invocation or receipt alone does not clear pending state. Compaction summaries, worker notifications, and messages from other agents do not approve work. The Operation and Exceptions of [Approval](../../protocol/approval.md) define actual input boundaries, advance approval, and the work that remains prohibited while waiting; the entry's Pending STOP and Interruption sections define report reconstruction; and each host's implementation `hosts/<host>/approval.md` ([Claude](../../hosts/claude/approval.md), [Codex](../../hosts/codex/approval.md)), folded into that operation's Implementation section on install, records the choice tool, receipt, and timeout facts with their observed versions and dates. The gate's source is [tools/ddl_gate.py](../../tools/ddl_gate.py); the generator copies it to `.claude/hooks/ddl_gate.py` and `.codex/hooks/ddl_gate.py` in the layouts.

### Project detection

The hook acts only in a DDL project. A project is one when its instruction file (`CLAUDE.md`, `.claude/CLAUDE.md`, or `AGENTS.md`, searched from the working directory up to the repository root or `$HOME`) contains the line `→ DDL-PROTOCOL`; both templates carry it, and the presence of `design.md` is not the criterion. In any other project every hook event (PreToolUse, Stop, UserPromptSubmit, SessionStart) returns at once: no STOP state, no Git review, no `design.md` injection, and `git commit` and `git push` run as usual. The decision is cached per session and recomputed at each user prompt and session start; the non-DDL fast path targets 30 ms or less per call. `python3 ddl_gate.py status` and `bin/doctor.sh` print one line saying whether the current directory is a DDL project and which file and line decided. This detection scopes the hook only: the user-level Claude settings `env` (subagent spawn depth 1) and `attribution` (empty) remain global settings of the merged file.

### Git content review

The gate's `prepare-git-review` command snapshots the staged contents, exact message, and requested push targets. It returns complete review detail and a host-specific `nativeRequest`; pass that request unchanged to the supported question tool. The report must name its generated review ID. Preparation data contains no approval flag. Before recognized ordinary commit/push calls, the hook checks the actual native request/result association and compares the live Git state with that prepared set, even while STOP is OPEN and under `never`. Hold, revision, timeout, receipts, unrelated answers, changed content, missing proof, and resumed preparations do not authorize those calls. A ready commit and its exact dependent push can share one answer.

This changes the default workflow: stage the proposed set for review, preserve unrelated user changes, then keep that index intact after approval. Supported ordinary forms use `git commit --cleanup=verbatim -m ...` or `-F ...` on a named branch, and one configured push remote with one branch/refspec. Follow-tags and recursive submodule pushes must be explicitly suppressed when configuration would otherwise expand the destination set. Unsupported options and Git actions stop with the reason; they are not silently removed. Review directories are private and remote credentials are omitted from the saved report and metadata.

Unprovable recognized reviews deny inside a running handler. The handler has a shorter Git-verification budget than the adapter timeout, but a host-level hook failure or timeout may still fail open. Arbitrary program internals, aliases, existing-process input, Git hooks that rewrite a commit, and concurrent changes between inspection and execution are outside a universal guarantee. The guard is not a tamper-proof authorization service for a hostile process that can edit its own transcript and state.

Regression tests use native-shaped reply fixtures, real disposable Git repositories and local bare remotes, and the installed adapter commands. These are simulated dispatch tests, not new live choice-submission tests in both apps. A separate live Codex desktop observation confirmed that the existing hook transport denies a call while a diagnostic pending marker exists and permits it after cleanup; it does not by itself prove the new content-review feature was deployed or exercised live.

### Push confirmation

The Codex native rule requests confirmation for literal `git push ...`. A separate hook guard rejects recognized static forms that miss that rule, such as Git global options or explicit wrappers. Use a separate canonical invocation with the tool's working directory set to the intended repository only when it preserves the original meaning; otherwise explain the limitation. The guard never rewrites commands or grants permission. Absolute host Git paths keep native executable resolution; arbitrary scripts, aliases, and dynamically built pushes remain outside this form check.

Explicit `bypassPermissions` and documented `dontAsk` modes waive only the push-form guard, not STOP or the Git content review. Sessions whose approval policy never prompts show no execution-time confirmation; the content review still applies. Claude installs no native `git push` permission rule: inside a DDL project the hook itself asks natively for the reviewed push, and its behavior under modes that bypass permissions is unverified. Claude disables attribution through settings; Codex adds no attribution.

### Native question observations

These observations are dated 2026-11-01 and do not establish support for every version or host.

**Claude Code 2.1.316.** Idle timeout settings are `60s`, `5m`, `10m`, and `never` (the default); Remote Control disables the idle timer. A 60-second timeout returned host-only `afkTimeoutMs: 60000`, even with selected but unsubmitted answers and source `user_temporary`. Explicit submission under the same settings omitted the field. The gate excludes non-null `afkTimeoutMs` results from human-input boundaries; interpreting a genuine answer as approval remains the agent's responsibility.

**Codex hosts.** The desktop host used for verification accepted click replies after final messages. Codex CLI 0.166.0 Default displayed an asynchronous selector, then erased it and restored the composer at turn completion; no answer arrived afterward. That route is not approval-capable. DDL explains the limitation and stops unapproved without typed-choice substitution or a mode switch to bypass permitted use.

The observed asynchronous function exposed only `questions`, `title`, and `options`, with no timeout argument. The app-server schema's deprecated `autoResolutionMs` and required `isBlocking` fields are separate from those function arguments. Neither the schema nor this observation establishes universal timeout behavior. A request receipt such as `accepted: true` is not a human answer.

## Validation

[Doctor](../../bin/ddl_setup.py) checks links and merged settings, checks that `dist/` is current, runs the gate suite, probes saved hook commands in a disposable home, checks the Codex native push rule separately, and prints whether the current directory is a DDL project and which file and line decided. It reports `N OK, M not OK` and exits 1 when a check fails. It does not certify native hook trust, dispatch on every transport, or the interactive approval UI.

For source changes, the repository's [Validation section](../../design.md#validation) is the declared check list. Useful focused checks are:

| Check | What it verifies |
|---|---|
| `python3 -I tools/check_ddl.py source` | The maintained sources, printing `SOURCE_OK`: command phases, directives, SWARM operand values, the shared Phase 0 lines read from the command template (the Example of Command authoring), the template in both host forms, the instruction templates' structure, the entry's instruction table, the fixed sections of the operations and implementations, the required Mapping rows of each implementation, operand and section rows, the literal strings commands write, exception rows, dated observations, tool names outside `hosts/`, links inside implementations, sentences of sixty or more characters repeated within or across files (P14), and the adapter files under `hosts/` with the gate's source |
| `python3 -I tools/check_ddl.py dist` | The trees the generator produces, built in memory, printing `DIST_OK`: each host's protocol skill holds the entry with its Host section folded from that host's `start.md`, the six operations with that host's implementation folded into their Implementation sections, and no `hosts/` directory or other host's implementation; every Reading map row points at an `#implementation` or `#host` fragment, every link resolves inside the skill, and no `{host}` placeholder remains (P12); the command twins and the instruction files pass the source checks; the gate copies equal `tools/ddl_gate.py`; the byte budget of each reading path and of the execution-time total holds on that host (P13); and `dist/` on disk, when present, equals the generated trees |
| `python3 -I tools/check_ddl.py docs` | Language-pair structure, glossary terms, current names and paths, and layout, printing `DOCUMENTS_OK` |
| `python3 tools/build.py --check` | `dist/` matches what the sources generate, file by file |
| `python3 -I tools/test_protocol.py` | The link walk over each host's generated tree and the rendered source, the build round-trip, the installer round-trip from a fixture's `dist/`, and the fourteen negative cases: name-only instruction rows, a Reading map row without an implementation, a `+++DETECT:` block without its header, invalid SWARM `max`/`batch`, a missing anchor, an undefined notebook mark, a missing schema section, a blank observed date, a tool name in an operation, a reading path over its byte budget, a sentence of sixty or more characters that appears twice, a Git review Example without a push, a Command authoring Example without a template fence, and a markdown link inside an implementation |
| `python3 -I tools/test_ddl_gate.py` | STOP and Git review handling through simulated dispatch and disposable Git repositories, and project detection: the marker line found or absent, the search up to the repository root or `$HOME`, the per-session cache, the non-DDL fast path, and the status line |
| `python3 -I tools/test_ddl_setup.py` | Build, installation, settings preservation, diagnostics, and removal in isolated homes and projects |

The source, dist, documentation, resource, and generation checks inspect maintained text and generated files; a passing source check counts the specification's units and does not establish that their content is complete or that a model follows the protocol. The setup suite runs separately from doctor so its install/doctor/uninstall rehearsal cannot recurse. Its isolated homes and projects exercise configured hook commands, not the native UI.

For live behavior checks, identify the host version, model and reasoning setting, session mode, and selected protocol source. Inspect actual tool and worker results; exclude restricted runs when use of the intended source cannot be confirmed. Host output formats also affect the evidence: on 2026-11-02, a persistent Codex 0.166.0 run confirmed command exit 0 through two default workers after the custom explorer's symlink failed with `ELOOP`; ephemeral JSON output did not establish the child results.

Keep conclusions specific to those conditions. In Claude Code 2.1.316 checks on 2026-11-02, Fable 5.1 xhigh read the entry and the host's start implementation that the validate/draft paths require, emitted `+++DDL_REPORT`, reported unavailable native selection, and left the draft unsaved; Haiku 5.5 low omitted the start implementation and a report marker. Such behavior checks do not establish native choice submission, hook enforcement, compaction or restart recovery, or token usage. Verify and report those separately; file-byte measurements describe loading size, not measured tokens.

## Documentation and translation

Keep the English/Japanese philosophy pairs aligned in meaning, heading structure, and examples. Each document links to its Git history; do not duplicate that history in the text. User-facing navigation points to the explanations, not the translation machinery.

Maintainers and translation agents use the [Japanese terminology reference](../ja/GLOSSARY.md). Its canonical path remains `docs/ja/GLOSSARY.md`. Follow it when maintaining the Japanese documents; operational command and skill instructions remain English except for literal artifact text, examples, and glossary data.
