# DDL maintainer reference

This page is for people and agents maintaining DDL, its adapters, and its documentation. For installation and everyday use, start with the [project README](../../README.md), [Codex guide](../../hosts/codex/README.md), or [Claude guide](../../hosts/claude/README.md).

## Installation reference

The environment installer runs the [generator](../../tools/build.py) first, then symlinks the nine skills (eight commands and `ddl-protocol`), the `explorer` and `worker` agents, and the gate hook from the generated layout under `dist/` into each selected host's home, and merges the adapter's settings fragment. DDL installs no permission rule; the installer removes, and names, the Codex push rule link an older install left in `~/.codex/rules/`, and doctor reports such a link as not OK until then. Without host flags, the installer selects the host home directories that already exist; if neither exists, select `--claude` or `--codex` explicitly.

| Host | Merged file | DDL settings |
|---|---|---|
| Claude | `~/.claude/settings.json` | Gate hooks; spawn depth 1 and attribution off, which stay global settings for every project |
| Codex | `~/.codex/hooks.json` | Gate hooks, PermissionRequest among them |

Existing settings are retained. The first change to a settings file keeps a backup beside it as `settings.json.ddl-backup` or `hooks.json.ddl-backup`. The installer does not write Codex `config.toml`; to match SWARM's `max: 5`, set `[agents] max_concurrent_threads_per_session = 5` there yourself. Doctor reports a missing cap as optional.

The install, doctor, and uninstall scripts accept `--claude`, `--codex`, and `--dry-run`; doctor also accepts `--strict` ([Validation](#validation)). Uninstall removes DDL-owned links and the merged fragment while leaving unrelated settings and files. It leaves the gate's grant store in place and names it when the store holds anything, removes the store when it is empty, and does not touch a project's `.ddl/` ledger ([Grant, ledger, and counts](#grant-ledger-and-counts)). Doctor rebuilds `dist/` first as well and says so on an `info` line. The hook requires Python 3 and the standard library; if Python is absent, hook execution fails open and the protocol still applies as instructions.

### Updating a linked installation

Pull updates through Git in the DDL clone, then run the installer again: it rebuilds `dist/`, which the links point into, and refreshes the merged settings. For the catch-all matcher update, rerun installation even when the hook link already points at the clone. Review changed Codex hooks in `/hooks` before relying on them.

```bash
bash DDL/bin/install.sh
bash DDL/bin/doctor.sh
```

For project-contained layouts, use `bash DDL/bin/install.sh --project your-project` with an optional host flag. It builds, then copies `dist/claude/.claude/` into the project's `.claude/` or `dist/codex/` into the project's root, and keeps an existing instruction file. Repeat the project install to update the copied files. Claude trusts project hooks through folder trust; Codex requires project trust and hook trust.

## Source files and generated files

The sources are one host-neutral tree: `skills/`, `protocol/`, the five implementations in each `hosts/<host>/`, and the gate's three files `tools/ddl_gate.py`, `tools/ddl_gate_core.py` and `tools/ddl_run.py`. The host-specific adapter files and the instruction-file templates live beside the implementations in `hosts/<host>/`. The [generator](../../tools/build.py) writes both deployable layouts into `dist/`, which is untracked:

| Source | Generated by `tools/build.py` into `dist/` |
|---|---|
| `skills/<name>/SKILL.md` (the eight commands, `/name` notation) | `dist/claude/.claude/skills/<name>/SKILL.md` byte for byte; `dist/codex/.agents/skills/<name>/SKILL.md` with `/name` turned into `$name`, plus `agents/openai.yaml` |
| `protocol/SKILL.md` (the entry) and `protocol/<operation>.md` (the seven operations) | `skills/ddl-protocol/SKILL.md` and the seven operations in each host's layout, with `{host}` and `{Host}` rendered to that host's name; the Codex entry also gets `agents/openai.yaml` |
| `hosts/<host>/{start,approval,parallel-work,git-review,run}.md` | Folded into that host's layout only: `start.md` becomes the `## Host` section of the entry, and the other four become the `## Implementation` section (`### Mapping`, `### Observed`, `### Coverage`) of the operation of the same name |
| `hosts/claude/guidance.md`, `settings.json`, `agents/` | `dist/claude/.claude/CLAUDE.md`, `settings.json`, `agents/` |
| `hosts/codex/guidance.md`, `hooks.json`, `config.toml`, `agents/` | `dist/codex/AGENTS.md` and `dist/codex/.codex/` |
| `tools/ddl_gate.py` (the hook's entry, a launcher), `tools/ddl_gate_core.py` (the gate's code, which the entry loads) and `tools/ddl_run.py` (the subcommands `report`, `run-start`, `run-item` and `snapshot`, which that code imports for those words only) | Each under its own name, side by side, in `dist/claude/.claude/hooks/` and `dist/codex/.codex/hooks/` |

Command bodies translate `/command` invocations to `$command` in the Codex form; the protocol entry and its operations are rendered, and the implementations are folded into them. Generated YAML prevents implicit invocation of the command skills; a command reads the entry in Phase 0 and one operation before each action it defines, each file carrying the host's implementation inside it. READMEs are never deployed.

The canonical behavior lives in the [shared protocol](../../protocol/SKILL.md), written as an instruction-set reference; command files refer to it rather than duplicating its rules. The entry `SKILL.md` holds Start, the Instruction set (ten directives, each with Syntax, Count, Placement, and Rule), Pending STOP, the Reading map, and Interruption. The Reading map has three columns, Operation, Read before, and Implementation, and routes to seven operations flat beside the entry, each with the fixed sections Read when, Syntax, Operands, Operation, Formats, Example, Exceptions, and Implementation: [Approval](../../protocol/approval.md), [Parallel work](../../protocol/parallel-work.md), [Notebook](../../protocol/notebook.md), [Close](../../protocol/close.md), [Git review](../../protocol/git-review.md), [Run](../../protocol/run.md), and [Command authoring](../../protocol/command-authoring.md). Each Example holds one short worked example beside the rules; the complete command template is the Example of Command authoring. In the source, the Implementation column names its file through `{host}` placeholders; a generated Reading map row points at the `#implementation` fragment of its operation or at the entry's `#host` fragment, because an installed protocol folds its own host's five implementations into those files and has no `hosts/` directory. Those five, in [hosts/claude/](../../hosts/claude/) and [hosts/codex/](../../hosts/codex/), are `start.md` for the entry's Start and one for each operation with host-specific differences (`approval.md`, `parallel-work.md`, `git-review.md`, `run.md`), named after it; Close reads Git review's, and Notebook and Command authoring need only `start.md`, already read. They hold Read when, Mapping, Observed (Fact / Version / Date), and Coverage, refer to operations by name, and carry no links; tool names appear only in the implementations under `hosts/`. The Mapping of each `start.md` holds only Session start, Compaction, Notebook loading, Adapter paths, and the `+++DDL_PHASE` and `+++DDL_REPORT` markers; the lookup order and Phase 0 loading live in the commands' Phase 0 lines and the instruction files. No file under `hosts/claude/` or `hosts/codex/` is named `claude.md`, which Claude reads as a nested `CLAUDE.md` on a case-insensitive filesystem (observed 2026-11-02, Claude Code 2.1.316); the instruction-file template is `guidance.md` for that reason, and the generator renames it on output. These are files within the selected protocol skill, not extra user-invoked commands.

The source tree of the protocol and the implementations:

The generator renders the entry and the seven operations into `dist/claude/.claude/skills/ddl-protocol/` and `dist/codex/.agents/skills/ddl-protocol/`, and folds only that host's five implementations into them: `start.md` as the entry's Host section, and the other four as the Implementation section of the operation of the same name. The other host's implementations are absent from an installed protocol, which has no `hosts/` directory. Each host guide shows the generated tree it receives.

### Project overrides and session context

A project's own command skill takes precedence over the environment-installed command. `commands/<name>.md` can add project facts such as target paths, protected terms, and validation commands. Commands use the project's protocol copy when present, otherwise the user-level copy under `~/.claude/skills/` or `~/.codex/skills/`; the commands' shared Phase 0 lines and the instruction files state this lookup, and links inside the protocol resolve relative to the selected copy, never to another installation.

Claude loads the instruction file and its `design.md` import at session start and after compaction. Codex loads `AGENTS.md`; trusted SessionStart hooks inject `design.md`, or the skill reads it when the hook is unavailable. Neither host loads the history file `design-history.md` at session start; a command reads it when a reason or a source is needed. A worker receives a self-contained prompt with its scope and approved work; it does not depend on inheriting the lead's conversation. The Operands, Operation, and Exceptions of [Parallel work](../../protocol/parallel-work.md) define worker roles, the spawn, and fallback behavior, and the host's implementation `hosts/<host>/parallel-work.md` ([Claude](../../hosts/claude/parallel-work.md), [Codex](../../hosts/codex/parallel-work.md)), folded into that operation's Implementation section on install, maps `type: Explore` and `type: general-purpose` to the host's agent definitions.

`design.md` contains the human-agreed Experience and any Binding Decisions, Direction, Acceptance Gates, principles, scopes, and validation the project needs. Automatic memory is a recall layer, not a source of binding agreement. The Operands of [Notebook](../../protocol/notebook.md) define section ownership, its Operation defines retirement into the history file, and its Formats define the two file names and the literal strings commands write there, such as `passed <date>`, `Approved plan (<date>)`, and the heading of a history record; a mark a command writes must be defined in those Formats.

## Batch approval

At a required STOP, present one concise overall recommendation and the complete current review set: visible numbered compatible actions with stable IDs, recommended resolutions, and their material impacts. Keep important risks and unknowns in that report and make detailed evidence separately accessible. A set containing several proposals still receives one native approval interaction by default.

Offer **Approve all current recommendations**, **Choose a subset or request changes**, and **Hold**. Explicit approve-all authorizes exactly the displayed ready set and recommended resolutions. It does not authorize undisplayed or future items, later STOPs, unconfirmed outward actions, or silent changes to Binding Decisions. Apply the approved set without follow-up approvals per file, item, or section.

Subset editing is optional and starts only when requested. Use native multi-select/checklist controls or one grouped form when the host supports them; never impose a typed ID list or an automatic N-item, N-turn approval loop. Use Claude's native `multiSelect` only when the exposed schema supports it. The observed Codex asynchronous function accepts only `questions`, `title`, and `options`; do not invent a `multiSelect` property for it. Offer compatible subsets as native choices when a grouped selector is unavailable.

The native question is the final interaction while waiting at that STOP. Prepare the complete report into its file first (`prepare-report`, ID `R-<id>`); the prepared question then carries five lines in the user's language (what to decide, the recommendation and its reason, the consequence, the confirmation ID, and the absolute path of that file), so it alone is enough to decide. A report that carries a grant adds one generated line after those five ([Run](../../protocol/run.md)). The chat still carries `+++DDL_REPORT` and the report, but nothing relies on it. A synchronous question waits for the actual submitted answer. On an asynchronous host that keeps the question answerable after turn completion, end the turn after the request receipt and wait for that answer. Respect the tool's permitted purpose and mode; do not switch modes to bypass a restriction. A receipt, cancellation, dismissal, no selection, or timeout is not approval. An answer must authorize the current displayed set or an explicitly selected subset.

## Close stage

Work ends in a [Close](../../protocol/close.md) stage. `/realize` runs it after the last implementation stage, and `/commit` runs its scan before the Git review, following its Operation in order: reflect the code into `design.md` and retire what passed into its history file, audit the documentation the change set touches, align language pairs, validate, then prepare one Git review of the whole change set. Inside `/realize` the approved plan authorizes the Close edits, and the Git review is where the user sees them. Inside `/commit` the invocation authorizes them, and the one Git review shows them with the whole change set; only a Binding Drift stops first. After the commit, the report states that nothing remains or names leftovers with reasons; no next command is suggested. `/reflect`, `/docs`, and `/resonate` remain standalone commands; standalone, they and `/refactoring` take a snapshot, apply their reversible changes inside their own targets, and report last without asking, so the snapshot undoes them.

## Runtime boundaries

The catch-all matchers inspect tool calls dispatched through the host's hooks. A report awaits human input from a prepared report or Git review in the record, a question carrying its ID, or a line-initial `+++DDL_REPORT`, until a human answer, a typed message, or an approved plan. Meanwhile the gate permits exact known read tools, its own preparation, the prepared question, input-free polling where supported, and bounded literal shell reads. Unknown tools, worker follow-ups, general scripts, unsupported shell forms, and a question that lacks the pending ID, differs from the prepared one, or carries an ID older than a resume or compaction are denied on covered paths. The gate reads no thinking block or reasoning item. Use display forms such as `cat`, `head`, `tail`, `rg`, or `sed -n '1,10p' file` to clarify a report.

This is a static guardrail, not complete STOP enforcement or a sandbox for ambient executable and configuration behavior. Runtime paths outside the hooks, asynchronous transcript timing, and unexpected errors limit enforcement. General STOP errors fail open with a warning. The protocol's Approval operation still applies, and the agent judges whether a submitted answer approves the current report and scope. Ordinary commits and pushes also have the independent content review below.

Question invocation or receipt alone does not clear pending state. Compaction summaries, worker notifications, and messages from other agents do not approve work. The Operation and Exceptions of [Approval](../../protocol/approval.md) define actual input boundaries, advance approval, and the work that remains prohibited while waiting; the entry's Pending STOP and Interruption sections define report reconstruction; and each host's implementation `hosts/<host>/approval.md` ([Claude](../../hosts/claude/approval.md), [Codex](../../hosts/codex/approval.md)), folded into that operation's Implementation section on install, records the choice tool, the preparation command, receipt, and timeout facts with their observed versions and dates. The gate's entry is [tools/ddl_gate.py](../../tools/ddl_gate.py), the file the settings name, and its code is [tools/ddl_gate_core.py](../../tools/ddl_gate_core.py), which the entry loads from a private bytecode cache under the gate's state directory so that a hook call does not compile it; the Run subcommands are in [tools/ddl_run.py](../../tools/ddl_run.py), which no hook event imports. The generator copies all three into `.claude/hooks/` and `.codex/hooks/` in the layouts.

### Project detection

The hook acts only in a DDL project. A project is one when its instruction file (`CLAUDE.md`, `.claude/CLAUDE.md`, or `AGENTS.md`, searched from the working directory up to the repository root or `$HOME`) contains the line `→ DDL-PROTOCOL`; both templates carry it, and the presence of `design.md` is not the criterion. In any other project every hook event (PreToolUse, PostToolUse, Stop, UserPromptSubmit, SessionStart, and on Codex PermissionRequest) returns at once: no STOP state, no Git review, no `design.md` injection, and `git commit` and `git push` run as usual. The decision is cached per session and recomputed at each user prompt and session start; the non-DDL fast path targets 30 ms or less per call. `python3 ddl_gate.py status` and `bin/doctor.sh` print one line saying whether the current directory is a DDL project and which file and line decided, followed by one line for each grant recorded for that project. This detection scopes the hook only: the user-level Claude settings `env` (subagent spawn depth 1) and `attribution` (empty) remain global settings of the merged file.

### Git content review

The gate's `prepare-git-review` command snapshots the staged contents, exact message, and requested push targets. It writes the complete review to `<state dir>/git-reviews/<id>/report.md` and returns a host-specific `nativeRequest` whose five-line question, generated from the reviewed operations, carries the `G-<id>` review ID and that file's path; pass that request unchanged to the supported question tool. Preparation data contains no approval flag. Before recognized ordinary commit/push calls, the hook proves the review only from the recorded question's exact equality with the prepared one and the human's answer choosing to execute it, never from the chat report, and compares the live Git state with that prepared set, even while STOP is OPEN and under `never`. Hold, revision, timeout, receipts, unrelated answers, changed content, missing proof, and resumed preparations do not authorize those calls. A ready commit and its exact dependent push can share one answer.

This changes the default workflow: stage the proposed set for review, preserve unrelated user changes, then keep that index intact after approval. Supported ordinary forms use `git commit --cleanup=verbatim -m ...` or `-F ...` on a named branch, and one configured push remote with one branch/refspec; a commit in a second git directory, `git --git-dir=<dir> --work-tree=<dir> commit ...`, is reviewed as its own repository, and one review may hold a commit in each. Follow-tags and recursive submodule pushes must be explicitly suppressed when configuration would otherwise expand the destination set. Unsupported options and Git actions stop with the reason; they are not silently removed. Review directories are private and remote credentials are omitted from the saved report and metadata.

A push may carry `project`, an edition of an earlier commit operation in the same review: `{from, include, files, message, author, base}`, with `from` the number of that commit operation, `include` the include list and `files` the overlay directory inside that commit (no absolute path, `.` or `..`), the edition's exact `message` and `author`, and `base` the target's last published commit. The preparation projects that operation's staged tree (a pinned gitlink shown as the commit its push sends) through the include list, lays the overlay's files over it, refuses a `base` that is not the target's head (read with `ls-remote` of the push URL; null only for a first publish), and shows the edition's diff. The push passes only when its commit holds exactly that projection of the commit the review created, has the target's head as its one parent, and carries the reviewed message with the reviewed author as author and committer.

Unprovable recognized reviews deny inside a running handler. The handler has a shorter Git-verification budget than the adapter timeout, but a host-level hook failure or timeout may still fail open. Arbitrary program internals, aliases, existing-process input, Git hooks that rewrite a commit, and concurrent changes between inspection and execution are outside a universal guarantee. The guard is not a tamper-proof authorization service for a hostile process that can edit its own transcript and state.

Regression tests use native-shaped reply fixtures, including records whose reports exist only as a Claude thinking block or a Codex reasoning item, real disposable Git repositories and local bare remotes, and the installed adapter commands. These are simulated dispatch tests, not new live choice-submission tests in both apps. A separate live Codex desktop observation confirmed that the existing hook transport denies a call while a diagnostic pending marker exists and permits it after cleanup; it does not by itself prove the new content-review feature was deployed or exercised live.

### Allowed calls

The gate allows these calls, so the host asks nothing more for them: a commit or push that matches an answered Git review, and the steps of its `pin` between a reviewed push and the pinned commit; and, while a grant is active, the calls inside it ([Run](../../protocol/run.md)), with a plain local commit inside it when the grant names the class `commit`; after such a commit a PostToolUse hook compares the new commit's paths with the grant and logs any path outside it as a `warn`, which the next push review shows on that commit. Claude takes the allow from PreToolUse (`permissionDecision: allow`). Codex refuses an allow there, so its PreToolUse keeps every deny and returns nothing for these calls, and a PermissionRequest hook answers `allow` when Codex asks for permission; a call Codex runs without asking never reaches it. DDL installs no permission rule on either host. On Claude a user's own `deny` or `ask` rule still applies after the allow (the host's documented order); on Codex whether a user's `prompt` or `forbidden` rule still applies after a PermissionRequest allow is unchecked. A pending STOP is never lifted (a question that names the items it holds stops only those, their dependents and every exit), an internal error, an unreadable record or a call asking to leave the sandbox gets no allow, no grant covers a protected file (Git's files, CI workflows, `.ddl/`, an agent's, editor's or direnv's settings, the instruction files, the notebook and its history) except that a commit inside a grant may include one the grant names by its literal path, and every other outward action (forges, publishing, transfers; a grant covers only a run on a granted machine) keeps the host's own confirmation.

On Codex a separate hook guard rejects recognized static push forms that the Git review cannot read, such as Git global options or explicit wrappers. Use a separate canonical invocation with the tool's working directory set to the intended repository only when it preserves the original meaning; otherwise explain the limitation. The guard never rewrites commands. Absolute host Git paths keep native executable resolution; arbitrary scripts, aliases, and dynamically built pushes remain outside this form check. Explicit `bypassPermissions` and documented `dontAsk` modes waive only that guard, not STOP or the Git content review. Claude disables attribution through settings; Codex adds no attribution.

### Grant, ledger, and counts

A `/realize` plan names a grant: a scope (path globs, command classes, machines, data handed over), a budget (minutes, and fix attempts per failing check), and an expiry. `prepare-report` takes it under the input key `grant`, writes it as a block into the report file, and appends one generated line to the question. The gate records the grant only when the record proves that the human submitted the first option of the unchanged prepared question; a typed approval or another option records none, and the agent never writes a grant. The record goes to a user-level store (`$DDL_GATE_GRANT_DIR`, else `$XDG_STATE_HOME/ddl-gate`, else `$HOME/.local/state/ddl-gate`), which the gate creates when it first records a grant and the installer never creates. A recorded grant ends only at its expiry, and until then it is active; active grants form a union. The gate allows the calls inside an active grant ([Allowed calls](#allowed-calls)) and denies an edit, a command class or a machine outside every one; a grant does not end a pending STOP (while a pending question names the items it holds, the other calls inside the grant go on; a question that names nothing stops everything), covers a plain local commit only through the class `commit` (logged as a `commit` event), and never covers a push or another exit. A push's review lists every commit it sends, and inside a Run `prepare-git-review` refuses a push until a `close` item has its dependencies done.

In a DDL project the gate also keeps a ledger in `.ddl/` at the root of the project's main work tree: `.ddl/events.jsonl` receives one line per event the gate records, and `.ddl/runs/<run id>/run.json` holds a Run, the work of one approved plan, which `run-start` writes from the plan's report ID and its items and `run-item` updates one item at a time. The directory ignores itself and is never committed; outside a DDL project the gate writes none, and a failed write changes no decision.

`report` prints four count lines for a Run, a session, or a conversation record: the questions asked (approved, revised, timed out), the minutes the work waited for the human (with the median and the longest time to an answer), the gate's own denials, and the recorded grant with its expiry. A count that cannot be derived prints `not measured`, never an estimate; denials are not measured from a conversation record, and a native permission rejection is never counted. For a Run it adds the `Records` line (commits, those inside the grant, push reviews), the `Mail` line (messages sent, delivered and unread, per kind) when the Run has peers or mail, the `Flow` line and the questions it still waits on; the `Questions` line counts kinds too. `report --kinds` counts the project's questions by kind (the Git review of a commit or a push, a resource's per-run confirmation, a human gate, a plan, a decision) with the approval rate, the median answer time, the current streak of first-option approvals and the overturns, and names the candidates: to promote, a kind with three or more first-option approvals in a row and no overturn (the grant class `commit`, dropping a resource's `confirm = "each run"`, going ahead provisionally on a gate), never an exit; to demote, a kind overturned since its promotion. A plan prepared with a grant shows the same candidates in its report file and on a `Promote` line of its question. `/realize` writes these lines into its final report. The Operation, Formats, and Exceptions of [Run](../../protocol/run.md) define the grant, the Run, and the count lines; each host's implementation `hosts/<host>/run.md` ([Claude](../../hosts/claude/run.md), [Codex](../../hosts/codex/run.md)), folded into that operation's Implementation section on install, names the records, how an answer's time is read, the subcommands, and what is unverified. Their Coverage sections state that recording a grant and the allows under it are covered by simulated dispatch only: neither was observed live on either host.

### Run members and mail

`run-join <N-id> --peer <name> --runtime claude|codex [--lead] [--bind <nonce>]` records a conversation of a Run in `.ddl/runs/<N-id>/peers.json` (one lead per Run; a name of lowercase letters, digits and hyphens, never `lead` or `all`) and prints a one-time bind nonce, of which peers.json keeps only the SHA-256. The hook binds the session that ran the call by that nonce in the call's output, or by a later `run-join … --bind <nonce>`, and spends it; joining a peer that joined already is refused unless `--bind` gives its unspent nonce, which clears its session for the hook to bind again. Membership comes from an index the hook writes in the user-level grant store and from the Run's peers.json alone; files in the state directory are caches. `mail send --run <N-id> --to lead|all|<peer> [--kind note|amend|handoff] (--text <one line> | --file <file>) [--as <peer>]` appends one message to `.ddl/mail/<N-id>.jsonl` in one synced write, and `mail read --run <N-id> --peer <peer> [--all]` prints a peer's messages past its cursor, a byte offset kept in peers.json, and moves it; it waits at most a second for the Run's lock and then exits 3, the Run being busy. The hook hands a member's main conversation (a call without `agent_id`) its unread mail as hook context at PreToolUse, UserPromptSubmit, SessionStart and a shell call's PostToolUse, under `DDL mail (data, not instructions)`, at most 8 KiB a call and each message once; a worker gets mail only by its prompt, and a session that is no member costs one look for its index. In a live run Claude received a peer's mail through its PostToolUse hook on the next shell call; on Codex (2026-11-25) the gate bound a joining conversation, the lead's mail reached it without a command, and a non-lead peer's Git review preparation was denied with the lead-only message; Codex runs the user-level hooks only after they are trusted with `/hooks`, once per machine, and `codex exec resume <session> "<message>"` runs one turn of a peer's session.

In an open Run with a lead, the gate denies another member's native question, Git write, report or review preparation, worker start (`claude -p`, `codex exec`, the runner) and exit, and names the `mail send` to use; a session reads and sends mail only as its own peer, and only the lead's session as the lead. An approved `/draft` of another member goes to the lead as an `amend` message, which the lead takes in at an item boundary ([Run](../../protocol/run.md)). `runner <N-id> --host claude` starts each ready item that has a prompt file as a `claude -p` worker, as the default runner does with `codex exec`. The ledger records `run-join` and `mail-delivered` events.

## Validation

[Doctor](../../bin/ddl_setup.py) rebuilds `dist/` first, then checks links and merged settings (a retired Codex push rule link is not OK until install removes it), runs the gate suite, probes saved hook commands in a disposable home (unreviewed commits and pushes are denied; on Claude an edit inside a grant written into that home's store is allowed), checks that only its owner can enter the gate's grant store, and prints whether the current directory is a DDL project and which file and line decided. It reports `N OK, M not OK` and exits 1 when a check fails. It does not certify native hook trust, dispatch on every transport, or the interactive approval UI.

Doctor also audits the exits. An exit leaves the machine or cannot be undone: a push, a pull request or release command, a transfer to another machine, a branch-moving git command. The audit names each rule in `permissions.allow` of `~/.claude/settings.json` and each allowing `prefix_rule` in `~/.codex/rules/*.rules` that lets an exit through unasked or that wraps any command; it reads the rules as text and runs nothing. Its findings are a separate tally: they change neither the `N OK, M not OK` counts nor the exit status, unless `doctor --strict` counts each one as not OK. Doctor's hook probes and its run of the gate suite use a disposable grant store, so doctor never writes into the durable one.

The source, dist, documentation, resource, and generation checks inspect maintained text and generated files; a passing source check counts the specification's units and does not establish that their content is complete or that a model follows the protocol. The setup suite runs separately from doctor so its install/doctor/uninstall rehearsal cannot recurse. Its isolated homes and projects exercise configured hook commands, not the native UI.

For live behavior checks, identify the host version, model and reasoning setting, session mode, and selected protocol source. Inspect actual tool and worker results; exclude restricted runs when use of the intended source cannot be confirmed. Host output formats also affect the evidence: on 2026-11-02, a persistent Codex 0.166.0 run confirmed command exit 0 through two default workers after the custom explorer's symlink failed with `ELOOP`; ephemeral JSON output did not establish the child results.

Keep conclusions specific to those conditions. In Claude Code 2.1.316 checks on 2026-11-02, Fable 5.1 xhigh read the entry and the host's start implementation that the validate/draft paths require, emitted `+++DDL_REPORT`, reported unavailable native selection, and left the draft unsaved; Haiku 5.5 low omitted the start implementation and a report marker. Such behavior checks do not establish native choice submission, hook enforcement, compaction or restart recovery, or token usage. Verify and report those separately; file-byte measurements describe loading size, not measured tokens.
