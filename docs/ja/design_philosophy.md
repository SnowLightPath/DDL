# Design-Doc Loop (DDL)

## ✨ Intent

人間とLLMがセッション、エージェント、ハーネスをまたいで設計方針を共有し続けることが目的です。

DDLは紋切り型のプロセスではなく、作りたいデザインの集まりです。

DDLドキュメントは成果物ではなく、設計がコードに反映されるまでの一時的なメモです。

> 詳細な背景理論、実践例、ガイドラインは [design_philosophy_extended.md](./design_philosophy_extended.md) を参照してください。
> すべてを読む必要はありません。必要なときに必要な部分だけ参照してください。

-----

## 🎯 Background: The Session Discontinuity Problem

人とLLMの協働には、記憶の切断の問題があります。

- 我々と同様に長大なコンテキストは的確に引き継ぐことは難しいです。
- 議論内容は我々と同様に忘れられます。
- LLMとのセッションは予期せず、消えたりします。

そこで、LLMでコードのデザインをメモとして共有することを考えます。

### In the Harness Era

Claude Code や Codex のようなエージェントのハーネスはいまでは指示ファイル、自動メモリ、長い会話の要約という自前の記憶を持っています。この記憶はエージェントが思い出すのを助けますが、エージェントが書いた部分は人間が合意した記録ではありません。また、エージェントが仕事を並列のサブエージェントに渡すと、サブエージェントはたいてい新しいセッションとして始まるため、記憶の切断はワーカーの数だけ増えます。

希少な資源はモデルの記憶から人間の注意へ移り、共有するメモは二つの役目を負うようになります。一つはセッションをまたいで設計を保つことで、もう一つはエージェントが走り出す前に、人間が何を決め、どこを見たいかを伝えることです。

-----

## 💡 Core Principle

```
Human ←→ Document ←→ LLM
              ↓
            Code
```

ドキュメントが我々とLLMをつなぎ、コードはドキュメントに基づいて書かれます。

ただし、実装中に設計の問題が見つかることもあります。そのときはドキュメントを更新します。

最終的にコードが正（source of truth）となります。DDLドキュメントはコードやdocsに統合され、不要になったら削除して構いません。形式にこだわる必要はない。

## 🔄 The Loop

```
      Draft
        ↓
Design Document ⇄ Code
   (Realize ↓  ↑ Reflect)
```

### Draft

**目的：** ユーザーの体験をデザインとして先に書く。

実装より先にユーザー側のコードを書きます。コードが使いやすいかを確認してから実装します。

```python
# Draft: 実装より先に使い方を書く
async with Client("https://api.example.com") as c:
    users = await c.get("/users")  # この使い方で良いか？
```

ライブラリでは言語がそのまま使い方になり、ストリーミング表示はフレームワークに依存することがあり、組織が基盤を指定することもあるように、体験と切り離せない決定もあります。Draft はこれらを **Binding Decisions** として記録し、各行に拘束する理由と出典（人間の言葉と日付、または、その行を載せた報告を人間が承認したこと）を添えます。

```markdown
## Binding Decisions
| Decision | Why it binds | Source |
|---|---|---|
| Next.js App Router | 書きながら伸びる回答と、画面ごとの読み込み中・エラー表示が体験の中心 | 「Next.jsでやりたい」「App Router で」(2026-10-17) |
```

実装までの道筋がすでに見えているときは、Draft がそれを段階・並列のレーン・人間が見たい点からなる **Direction** として記録します。Direction は見通しであって約束ではありません。**Acceptance Gates** には作業を終えたときに成り立つべきこと、すなわち通るべきコマンドと人間が与える承認を書きます。Acceptance Gates は作業が受け入れられた時点で役目を終え、削除されます。

拘束できるのは人間だけであり、LLM が提案した技術は人間が選ぶまで何も拘束しません。コードにすでにある技術は既存の前提であり、コマンドは報告に示しますが design.md には記録しません。その技術は人間が理由を示したときにだけ Binding Decision になります。

### Realize

**目的：** デザインに基づいてコードを書く。

ドキュメントの方針と Binding Decisions に沿ってコードを実装します。Direction には理由がない限り従い、外れたときはそう伝え、人間の承認点では止まります。

### Reflect

**目的：** 実装結果をドキュメントに反映する。

実装してみて分かったことがあれば、ドキュメントを修正します。また、コードを Binding Decisions と照らし合わせ、終わった Direction を実際に起きたことで置き換えます。

コードが設計を追いこすほど、キーボードが走ることもあると思います。ハーネスの時代には、キーボードを走らせているのがエージェントの指であることも多いでしょう。

---

RealizeとReflectは概ね逆関数です。

## 🤝 Roles: Human and LLM

DDLにおける我々とLLMは対等な関係です。

|       | Human              | LLM                    |
|-------|--------------------|------------------------|
| 強み  | 最初の直感、長期視野、忍耐 | 技術知識、パターン認識、言語化 |
| 弱み  | 網羅性、実装の詳細       | 短期バイアス              |

我々がペースを制御し、LLMの短期バイアスを補正します。

エージェントが長く並列に走るようになると、我々の役目は具体的になります。何を拘束するか、どこを見るかを決めてその承認点で承認し、承認点のあいだはエージェントに任せます。

-----

## 🌊 Stay Flexible

DDLは厳格な手順ではありません。

- Draftを飛ばしていきなりRealizeしても構いません
- ドキュメントを書く前にコードが完成しても構いません

作業が進むときは進めてください。

大事なのは、作業後にドキュメントを更新すること（Reflect）です。

## ⚠️ Anti-Patterns

| Pattern                      | Problem                          |
|------------------------------|----------------------------------|
| ドキュメントなしでコードだけ書く    | 次のセッションで文脈が分からなくなる      |
| プロセスを厳格に守ろうとする       | DDLは厳格な手順ではない              |
| LLMに全部任せる                | Humanの判断や長期視点が入らない        |
| Humanが全部やる               | LLMの言語化・技術知識を活かせない       |
| ツール化を目的にする             | 目的が先で、ツールは手段              |
| DDLドキュメントを永続化しようとする | 不要になったら削除すべき              |
| 形式に囚われる                  | DDLは一時的なメモ                   |
| エージェントに技術を黙って選ばせる   | 誰も合意していない決定がコードを縛る      |
| ハーネスの記憶を設計とみなす       | エージェントは覚えているが、人間は合意していない |
| Direction を約束として扱う        | 見通しが固まり、誰も見直さない計画になる   |

## 📋 Summary

DDLは厳密な方法論ではなく、目的やデザインの集まりです。

我々とLLMがセッション、エージェント、ハーネスをまたいでデザインを共有し続けるためのメモです。

最終的にコードが正（source of truth）となります。DDLドキュメントは不要になったら削除します。

> **Tool-Assisted Option**: [Claude Code](../../examples/claude-commands/) (`/draft`, `/realize`, `/reflect` + サポートコマンド) | [OpenAI Codex](../../examples/codex-skills/) (`$draft`, `$realize`, `$reflect` + サポートスキル)
