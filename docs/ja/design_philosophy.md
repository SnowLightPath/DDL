# Design-Doc Loop (DDL)

## Intent

人間と LLM はセッション、エージェント、ハーネスをまたいで設計原則を共有し続けます。

DDL は作りたい設計の集まりであり、進め方は柔軟です。ドキュメントは設計がコードに反映されるまでの一時的なメモとして使います。

詳しい背景理論、例、ガイドラインは[詳説版](./design_philosophy_extended.md)にあります。必要なときに必要なものだけを参照してください。

## 背景: セッションの断絶という問題

LLM との協働開発にはセッションの断絶という問題があります。

- 一つのエージェントが覚えていることは、次のセッション、エージェント、ハーネスからは見えません
- エージェントが覚えていることは、人間が合意したことではありません
- セッションが抱えるものが増えるほど、そのうちモデルが思い出せる割合は減るので、コンテキストは人間と同じくモデルにとっても予算です

そこで、コードの設計をメモとして LLM と共有します。

### ハーネス時代

Claude Code や Codex のようなエージェントのハーネスはいまでは指示ファイル、自動メモリ、長い会話の要約という自前の記憶を持っています。その記憶はエージェントの想起を助けますが、エージェントがそこに書いたものは人間が合意した記録ではありません。

並列に働くサブエージェントはたいてい新しいセッションとして始まるため、ワーカーが増えるたびに断絶も広がります。共有するメモは作業に入る前の各エージェントに人間が固定したことと確認したいところを伝えます。

希少な資源は人間の注意と一つのセッションが抱えられるコンテキストです。共有するメモはセッションをまたいで設計を保ち、各エージェントに必要なコンテキストを渡します。

ハーネスはループの一部を担うこともできます。ハーネスが `hook`、エージェント定義、取り込みを備えているところでは、DDL のアダプタが STOP、ワーカーの役割、メモをコンテキストに載せ続けることを支えます。仕組みで執行できる範囲は実行環境によって異なり、執行できない部分にも同じ規則が指示として適用されます。

## 中核の原則

```
Human ←→ Document ←→ LLM
              ↓
            Code
```

ドキュメントが人間と LLM をつなぎ、コードはドキュメントに基づいて書かれます。

ただし、実装の途中で設計の問題が見つかることもあり、そのときはドキュメントを更新します。

最終的にはコードが正（source of truth）になります。DDL のドキュメントはコードや docs に統合され、不要になった内容は削除されるか履歴ファイルへ移されます。形式にこだわる必要はありません。

## ループ

```
      Draft
        ↓
Design Document ⇄ Code
   (Realize ↓  ↑ Reflect)
```

### Draft

**Intent:** ユーザー側の体験を先に書く。

コードを実装する前に、そのコードがどう使われるかを書きます。API が使いやすいかを確かめてから実装します。

```python
# Draft: 実装の前に使い方を書く
async with Client(
    "https://api.example.com"
) as c:
    users = await c.get("/users")
```

体験から切り離せない決定もあります。ライブラリの言語は使い方そのものであり、ストリーミングのインターフェースはフレームワークに依存することがあり、組織がプラットフォームを指定することもあります。Draft はこれらを **Binding Decisions** として記録し、各決定が実装を拘束する理由と出どころを添えます。

たとえば回答をストリーミングで表示する画面なら、次のような決定を記録します。

> **決定:** Next.js App Router。
>
> **拘束する理由:** 回答が書かれるそばから届き、ルートごとの読み込み状態とエラー状態が体験の中核になります。
>
> **出どころ:** 「Next.js で作りたい」「はい、App Router で」(2026-10-17)。

出どころは人間の発言と日付か、その決定を載せた報告への人間の承認です。

<details>
<summary>design.md に貼り付ける記述を見る</summary>

```markdown
## Binding Decisions
| Decision | Why it binds | Source |
|---|---|---|
| Next.js App Router | 回答が書かれるそばから届き、ルートごとの読み込み状態とエラー状態が体験の中核になる | 「Next.js で作りたい」「はい、App Router で」(2026-10-17) |
```

</details>

Draft はすでに見えている実装への道筋を **Direction** として記録し、段階、並列のレーン、人間が確認したい地点を書き並べます。Direction は見通しであって契約ではありません。

**Acceptance Gates** には作業の完了時に満たされているべきこと、すなわち通るべきコマンドと人間が与える承認を書きます。Acceptance Gates は作業が受け入れられた時点で退役します。

拘束するのは人間だけです。LLM は技術を提案できますが、その技術は人間が選ぶまで何も拘束しません。

コードにすでにある技術は既存の前提であり、コマンドは報告でそれを示し、design.md には記録しません。それが Binding Decision になるのは人間が理由を述べたときだけです。

### Realize

**Intent:** 設計原則に基づいてコードを書く。

文書化された原則と Binding Decisions に従ってコードを実装します。Direction には従わない理由がない限り従い、外れるときはその旨を述べます。人間のゲートでは止まります。

### Reflect

**Intent:** 実装の結果に基づいてドキュメントを更新する。

実装から学んだことがあれば、ドキュメントを更新します。コードを Binding Decisions に照らし、終わった Direction は実際に起きたこととともに履歴ファイル `design-history.md` へ移し、design.md にはいまの設計だけを残します。ツールを使う流れでは Reflect が Realize の終わりに Close 段階として走り、作業を終える 1 回のコミットの前に済みます。

指がキーボードの上を速く走りすぎてコードが設計を追い越すこともあります。ハーネス時代には、その指はエージェントのものであることが多くなりました。

Realize と Reflect はおおむね逆関数です。

## 役割: 人間と LLM

DDL では人間と LLM は対等なパートナーです。

|       | 人間               | LLM                    |
|-------|--------------------|------------------------|
| 強み | 最初の直感、長期の視野、忍耐 | 技術知識、パターン認識、言語化 |
| 弱み | 網羅性、実装の詳細 | 短期バイアス |

人間がペースを制御し、LLM の短期バイアスを補正します。

エージェントが長く並列に走るようになると、人間の分担は具体的になります。すなわち、何を拘束するかを決め、どこを確認するかを決め、そのゲートで承認することです。エージェントはゲートのあいだで働きます。

人間の注意は予算です。作業がいちばん長く待つのは人間の確認であり、質問を重ねるほど承認は形だけになるので、DDL は人間の注意深さに頼らず、設計で質問を減らします。通常の経路で DDL が人間に尋ねるのは設計を決めるとき（下書き、Binding Decision や原則の変更）、計画を許諾と一緒に承認するとき、design.md が名指しした人間のゲートを通るとき、そして push のような出口や、許諾の及ばないコミットの前です。検査の失敗や変更への秘密情報の混入のような検出が起きたときも、作業は止まります。許諾の内で戻せて手元にとどまる作業は尋ねずに進みます。`/reflect` や `/docs` のように単独で呼んだコマンドは保存点を作ってから戻せる変更を適用し、そのあとで報告します。ただし、Binding Decision、原則、保証した振る舞いを変える変更については、コマンドは適用の前に尋ねます。`/realize` の最後の報告は質問の数、作業が人間を待った時間、ゲートの拒否、許諾を数の行に載せるので、質問と待ちが数で見えます。報告は質問を種類（計画、確認、Git、ほか）ごとにも数え、Run ではコミットと送信の確認の数を `記録` の行に載せます。

許諾は `/realize` の計画が作業に定める範囲、予算、期限です。範囲は作業が編集してよいパス、走らせてよいコマンドの種類（ビルド、テスト、検査など）、使ってよいマシンとサービス、それらに渡すデータの種類を名指しします。人間が計画の質問で承認の選択肢を送信すると、ゲートの `hook` がその許諾を記録します。期限までのあいだ、ゲートはそのパスの編集、その種類のコマンド、読み取りを許可するので、DDL もホストもそれらについて尋ねません。ゲートは許諾の外の編集、コマンドの種類、マシンを拒み、許諾を広げるには見直した計画の承認が要ります。許諾は STOP を終わらせず、待機中の質問が止める項目を名指ししているあいだだけ、許諾の内のほかの作業を進めさせます。なお、項目を名指ししない質問はすべての作業を止めます。また、許諾は Git のファイル、指示ファイル、ノートのような保護されたファイルの編集も、push のような出口も許しません。許諾がコマンドの種類 `commit` を名指ししていれば、ステージしたファイルがすべて許諾の内にある通常の手元のコミットは尋ねずに通り、ゲートがそれを台帳に記録して数えます。保護されたファイルを含められるのは許諾がそのパスをそのまま名指ししたときだけです。こうして、コミットを細かく残したまま、承認は送信のときの 1 回にまとまります。出口のままの push では、1 回の確認が送るすべてのコミットを示します。Run の中では、計画の `close` の項目の依存が済むまでゲートが push を断ります。

エージェントはこのマシンで動き、リモートのマシンは渡されたものを走らせるだけです。マシンとサービスの名前は利用者ごとに置くリソースの表が持ち、表の形式は DDL が決めます。許諾はこの名前でマシンとサービスを名指しし、ゲートは表に無い名前と、リソースが受け取らない種類のデータを断ります。受け渡しは追跡されたファイル（または名指しした保存点のファイル）から保護されたファイルと秘密情報に見える名前のファイルを除き、履歴のない 1 つのコミットにしてマシンの使い捨ての写しへ送ります。ゲートが持ち帰るのは出力の行、ファイルのハッシュ、終了コードだけです。リモートのマシンにはエージェント、鍵、会話の記録、承認のどれも渡さず、持ち帰ったものは指示ではなくデータとして扱います。表が実行のたびの確認を求めるリソース（たとえば有料のクラスタやクラウドのサービス）には許諾が及びません。そうしたリソースでは実行のたびに、人間がそのコマンドやプロンプトそのものに与えた確認が要り、確認は 1 回で使い切られます。そうしたサービスの呼び出しも、サービスへのあらゆる書き込みも、確認を確かめるゲートの `service` だけを通ります。一方で、エージェントが直接呼んだプラグインはゲートの外にあり、そこではこの規則が指示として働きます。

質問は自分が止める Run の項目を名指しできます。待機中の質問がどれも項目を名指ししているあいだ、ゲートはその項目と依る項目の外にある許諾の内の編集と、パスを名指しするテストや検査だけを進めさせます。質問は STOP を待機中にせずに貯めておくこともできます。リードは人間が戻ったときか止めずに済む仕事が尽きたときに、貯めた質問をまとめて尋ねます。見込みの質問では、リードが保存点を作ってから推奨の選択肢で先に進めますが、推奨そのものは承認になりません。回答が出るまで、ゲートはこのマシンから出る呼び出しを拒みます。覆った選択はリードがゲートの `restore` で保存点から戻します。Run の最後の報告はまだ待っている質問を `[見込み]`、`[待ち]`、`[出口]` の印つきで並べます。

1 つの Run はどちらのホストの複数の会話でも共有できます。人間に尋ね、記録し、送るのはそのうちの 1 つであるリードだけです。ほかの会話がリードと話す手段は便りだけです。ゲートの `hook` はその便りを、会話の次のツール呼び出しの手前でデータとして渡します。ほかの会話で承認された `/draft` は改定としてリードに届き、次の項目の境界で取り込まれます。計画は質問の種類について上げる候補と下げる候補も示します。質問の種類は 3 回以上続けて承認され一度も覆されなければ次の計画に入れる候補になり、そのあと覆されれば外す候補になります。ただし、出口はどちらの候補にもなりません。候補を採るかどうかは計画を承認する人間が決めます。

人間の判断が必要なときは、エージェントが今回の確認全体に対する推奨案を示し、両立する作業とその影響を短い番号付きの一覧にまとめます。重要なリスクや未確認事項は本文に残し、詳しい根拠は必要なときに別に確認できるようにします。

人間は実行環境の質問画面で**「すべて承認」**、**「一部を選ぶ・修正する」**、**「保留」**から一度で選び、必要なら自由記述を添えます。「すべて承認」が対象とするのは表示中の今回の提案のうち実行できる推奨案と明記された解決策だけです。エージェントはその範囲を適用し、項目、ファイル、節、言語、状態ごとに承認を求め直しません。今後の STOP、承認した選択肢に明記されていない外に出る操作、提示していない Binding Decision の変更は承認されません。

両立しない案を同時には承認できないため、エージェントは両立する内容をまとめた計画案を示すか、未解決の部分を保留します。個別の選択は人間が求めたときに使い、できるだけ実行環境のチェックリストや複数項目をまとめた画面で一度に送信します。質問を何度も繰り返したり、項目の番号を文章で入力させたりする方法は基本にしません。

作業を許可するのは現在の報告とスコープを承認する実際の送信回答だけです。詳細や修正の依頼、キャンセル、画面を閉じる操作、未回答、時間切れは承認になりません。

完了した作業や読み取り専用の作業結果を伝える報告は、それ自体への承認を求めません。次の作業に人間の判断が必要な場合は、その作業を示して選択を求めます。選択しても、その作業の人間のゲートが免除されるわけではありません。

承認用の質問画面を使えるかどうかはホストとモードによって異なります。使えない場合や承認への利用が認められていない場合、エージェントは制約を説明して停止し、自動的に文字入力の選択肢へ置き換えません。質問の受け付け通知も人間の回答ではありません。

作業が長く並列に流れるとき、DDL は次の原則を守ります。どれもいま実装されている形で書きます（根拠の研究は[詳説版](./design_philosophy_extended.md#37-run-の原則)にあります）。

- **用意できた仕事があるかぎり枠を空けません。** ワーカーが終わるたびに用意できた次の項目が始まり、Codex ではゲートの `runner` が、Claude では完了の通知を受けたリードが補充します。枠の使われ方は見せますが、使い切ることは目標にしません。
- **エージェントはこのマシンで動き、リモートのマシンは渡されたものを走らせるだけです。** 会話、承認、鍵はこのマシンにとどまり、リモートのマシンには使い捨ての写しだけを置きます。
- **保存、記録、送信を分けます。** 人間が中身で確かめるのは送るすべてのコミットを確認で示す push と、許諾の外のコミットです。保存点、許諾の内のコミット、受け渡しは計画で範囲を確かめ、ゲートが記録します。
- **承認は段ではなく操作の種類で決めます。** 人間に尋ねるのは設計を決めるとき、計画と許諾を承認するとき、作業がこのマシンの外へ出る前です。止めるのは答えに依る仕事だけであり、時間切れは何も決めません。
- **design.md は現在形で、履歴は過去形で書きます。**
- **人間の注意は予算です。** 質問は注意深さではなく設計で減らし、その数を数えます。
- **人数ではなく直列の部分を減らします。** リードは書き手を独立した項目の数までにとどめ、余った枠を確かめと下調べに充てます。
- **確かめは書き手から独立させます。** リードは確かめる役に書き手の会話を見せず、差分と受け入れの条件だけを渡します。通過を決めるのは実行できる検査です。
- **してはいけないこと**は下のアンチパターンに挙げます。

## 柔軟に

DDL は厳格な手順ではありません。

- 望むなら Draft を飛ばして Realize に直行しても構いません
- それでうまくいくなら、ドキュメントを書く前にコードを仕上げても構いません

作業が流れているときは、流れるに任せてください。

大事なのは作業のあとにドキュメントを更新し（Reflect）、作業を閉じるコミットの前にそれを済ませることです。

## アンチパターン

| パターン                      | 問題                          |
|------------------------------|----------------------------------|
| ドキュメントなしでコードを書く | 次のセッションが設計なしで始まる |
| プロセスに厳格に従う | DDL は厳格な手順ではない |
| LLM に全部やらせる | 人間の判断と長期の視点が欠ける |
| 人間が全部やる | LLM の言語化と技術知識が使われない |
| ツール化を目的にする | 意図が先で、ツールは手段 |
| DDL のドキュメントを永続させようとする | 不要になったら削除する |
| 形式に囚われる | DDL は一時的なメモ |
| エージェントにスタックを黙って選ばせる | 誰も合意していない決定がコードを拘束する |
| ハーネスの記憶を設計として扱う | エージェントは覚えているが、人間は合意していない |
| Direction を契約として扱う | 見通しが固まって誰も見直さない計画になる |
| 要約から承認する | コンパクション（会話の圧縮）を経た会話は報告ではない。人間は目の前にあるものを承認する |
| 許諾の内の作業について尋ねる | 承認が形だけになり、作業は何も変えない質問を待つ |
| 確認を済ませた出口でもう一度尋ねる | 人間は同じ中身をもう一度見る。Git の確認が 1 回だけの確認である |
| 期限のない許諾を作る、許諾を黙って広げる | 承認が与えられた計画を越えて残り、広がる |
| 戻せないことを見込みで進める | 覆った答えを取り消せない。見込みには保存点が要り、答えが出るまで何もマシンの外へ出ない |
| 見込みの上に見込みを重ねる | 1 つの答えが覆ると両方を戻すことになる。ゲートはほかの見込みの質問が止める項目に重なる見込みの質問を断る |
| 人間がいないあいだに全体を止める質問を出す | すべてが 1 つの答えを待つ。質問は止める項目を名指しし、許諾の内の残りの作業は進む |
| 用意できた項目があるのに枠を空ける、波を待つ | 作業が依っていないものを待つ。ワーカーが終わるたびに補充すれば、枠は使われ続ける |
| 稼働率 100% を目標にする | 目標は仕事があるのに空いている枠を無くすことであり、枠を埋め切ることではない |
| 独立した項目の数を超えて書き手を足す | 書き手を増やしても直列の部分は縮まず、誤りが増える |
| 書き手に自分の仕事を確かめさせる | 書き手の文脈を共有する確かめは甘くなる。通過を決めるのは実行できる検査である |
| 出口のゲートを回り道する（ssh の向こうの Git、スクリプトの中の Git、別の転送） | 外へ出るものが人間の 1 回の確認を通らない |

## まとめ

DDL は一時的なメモを使い、人間と LLM がセッション、エージェント、ハーネスをまたいで目的と設計を共有し続けることを支えます。実装から学んだことに合わせ、ループも柔軟に進めます。

最終的にはコードが正（source of truth）になります。DDL のドキュメントは不要になったら削除してください。

DDL は保存、記録、送信を分けて扱います。保存点は作業ツリーを `refs/ddl/snapshots/` の下のコミットとして保存し、枝も index もファイルも動かさないので、DDL は保存点の前に質問を置きません。許諾の内ではゲートがその呼び出しを許可し、単独のコマンドのように許諾がないときはホスト自身の権限の設定がその呼び出しを決めます。人間が中身で確かめるのは push と、どの許諾も及ばない枝のコミットであり、どちらも 1 回の Git の確認で見ます。許諾に `commit` があれば、許諾の内の手元のコミットはゲートが尋ねずに記録します。同じ確認案のコミットから作った公開版も push で送れます。ゲートはその push を、送るコミットが公開版とちょうど一致するときだけ通します。

Git に記録・送信する前にエージェントは最終差分、正確なメッセージ、送信先を確認案のファイルに書いて示します。同時に判断できる一式は、標準の選択画面で 1 回にまとめて承認します。その質問は確認 ID とファイルの場所を載せるので、人間は質問だけで判断できます。STOP の待機が解除されていても、`hook` は通常の commit・push（許諾の内のコミットを除く）をその確認案と照合します。実装前の承認や通常の返答だけでは通らず、内容が変われば再確認します。回答済みの確認案と一致する呼び出しは `hook` が許可するので、ホストは重ねて尋ねません。ただし、利用者が自分の権限規則で尋ねるとした呼び出しはそのまま尋ねられ、Codex では PermissionRequest による許可をまだ実機で確かめていません。対象は `hook` が受け取る呼び出しであり、実行環境の制約は別に記録します。Close 段階がその確認の前に design.md と文書を最新にするので、作業は 1 回のコミットで終わり、あとに続くコマンドはありません。
