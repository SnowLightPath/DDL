# Design-Doc Loop (DDL)

## Intent

人間と LLM はセッション、エージェント、ハーネスをまたいで設計原則を共有し続けます。

DDL は作りたい設計の集まりであり、進め方は柔軟です。ドキュメントは設計がコードに反映されるまでの一時的なメモとして使います。

詳しい背景理論、例、ガイドラインは[詳説版](./design_philosophy_extended.md)にあります。必要なときに必要なものだけを参照してください。

## 背景: セッションの断絶という問題

LLM との協働開発にはセッションの断絶という問題があります。

- 一つのエージェントが覚えていることは、次のセッション、エージェント、ハーネスからは見えません
- エージェントが覚えていることは、人間が合意したことではありません
- セッションが抱えるものが増えるほど、そのうちモデルが思い出せる割合は減るので、コンテキストは人間と同じくモデルにとっても予算です

そこで、コードの設計をメモとして LLM と共有します。

### ハーネス時代

Claude Code や Codex のようなエージェントのハーネスはいまでは指示ファイル、自動メモリ、長い会話の要約という自前の記憶を持っています。その記憶はエージェントの想起を助けますが、エージェントがそこに書いたものは人間が合意した記録ではありません。

並列に働くサブエージェントはたいてい新しいセッションとして始まるため、ワーカーが増えるたびに断絶も広がります。共有するメモは作業に入る前の各エージェントに人間が固定したことと確認したいところを伝えます。

希少な資源は人間の注意と一つのセッションが抱えられるコンテキストです。共有するメモはセッションをまたいで設計を保ち、各エージェントに必要なコンテキストを渡します。

ハーネスはループの一部を担うこともできます。ハーネスが `hook`、エージェント定義、取り込みを備えているところでは、DDL のアダプタが STOP、ワーカーの役割、メモをコンテキストに載せ続けることを支えます。仕組みで執行できる範囲は実行環境によって異なり、執行できない部分にも同じ規則が指示として適用されます。

## 中核の原則

```
Human ←→ Document ←→ LLM
              ↓
            Code
```

ドキュメントが人間と LLM をつなぎ、コードはドキュメントに基づいて書かれます。

ただし、実装の途中で設計の問題が見つかることもあり、そのときはドキュメントを更新します。

最終的にはコードが正（source of truth）になります。DDL のドキュメントはコードや docs に統合され、不要になったら削除されます。形式にこだわる必要はありません。

## ループ

```
      Draft
        ↓
Design Document ⇄ Code
   (Realize ↓  ↑ Reflect)
```

### Draft

**Intent:** ユーザー側の体験を先に書く。

コードを実装する前に、そのコードがどう使われるかを書きます。API が使いやすいかを確かめてから実装します。

```python
# Draft: 実装の前に使い方を書く
async with Client(
    "https://api.example.com"
) as c:
    users = await c.get("/users")
```

体験から切り離せない決定もあります。ライブラリの言語は使い方そのものであり、ストリーミングのインターフェースはフレームワークに依存することがあり、組織がプラットフォームを指定することもあります。Draft はこれらを **Binding Decisions** として記録し、各決定が実装を拘束する理由と出どころを添えます。

たとえば回答をストリーミングで表示する画面なら、次のような決定を記録します。

> **決定:** Next.js App Router。
>
> **拘束する理由:** 回答が書かれるそばから届き、ルートごとの読み込み状態とエラー状態が体験の中核になります。
>
> **出どころ:** 「Next.js で作りたい」「はい、App Router で」(2026-10-17)。

出どころは人間の発言と日付か、その決定を載せた報告への人間の承認です。

<details>
<summary>design.md に貼り付ける記述を見る</summary>

```markdown
## Binding Decisions
| Decision | Why it binds | Source |
|---|---|---|
| Next.js App Router | 回答が書かれるそばから届き、ルートごとの読み込み状態とエラー状態が体験の中核になる | 「Next.js で作りたい」「はい、App Router で」(2026-10-17) |
```

</details>

Draft はすでに見えている実装への道筋を **Direction** として記録し、段階、並列のレーン、人間が確認したい地点を書き並べます。Direction は見通しであって契約ではありません。

**Acceptance Gates** には作業の完了時に満たされているべきこと、すなわち通るべきコマンドと人間が与える承認を書きます。Acceptance Gates は作業が受け入れられた時点で退役します。

拘束するのは人間だけです。LLM は技術を提案できますが、その技術は人間が選ぶまで何も拘束しません。

コードにすでにある技術は既存の前提であり、コマンドは報告でそれを示し、design.md には記録しません。それが Binding Decision になるのは人間が理由を述べたときだけです。

### Realize

**Intent:** 設計原則に基づいてコードを書く。

文書化された原則と Binding Decisions に従ってコードを実装します。Direction には従わない理由がない限り従い、外れるときはその旨を述べます。人間のゲートでは止まります。

### Reflect

**Intent:** 実装の結果に基づいてドキュメントを更新する。

実装から学んだことがあれば、ドキュメントを更新します。コードを Binding Decisions に照らし、終わった Direction は実際に起きたことに書き換えます。

指がキーボードの上を速く走りすぎてコードが設計を追い越すこともあります。ハーネス時代には、その指はエージェントのものであることが多くなりました。

Realize と Reflect はおおむね逆関数です。

## 役割: 人間と LLM

DDL では人間と LLM は対等なパートナーです。

|       | 人間               | LLM                    |
|-------|--------------------|------------------------|
| 強み | 最初の直感、長期の視野、忍耐 | 技術知識、パターン認識、言語化 |
| 弱み | 網羅性、実装の詳細 | 短期バイアス |

人間がペースを制御し、LLM の短期バイアスを補正します。

エージェントが長く並列に走るようになると、人間の分担は具体的になります。すなわち、何を拘束するかを決め、どこを確認するかを決め、そのゲートで承認することです。エージェントはゲートのあいだで働きます。

人間の判断が必要なときは、エージェントが今回の確認全体に対する推奨案を示し、両立する作業とその影響を短い番号付きの一覧にまとめます。重要なリスクや未確認事項は本文に残し、詳しい根拠は必要なときに別に確認できるようにします。

人間は実行環境の質問画面で**「すべて承認」**、**「一部を選ぶ・修正する」**、**「保留」**から一度で選び、必要なら自由記述を添えます。「すべて承認」が対象とするのは表示中の今回の提案のうち実行できる推奨案と明記された解決策だけです。エージェントはその範囲を適用し、項目、ファイル、節、言語、状態ごとに承認を求め直しません。今後の STOP、承認した選択肢に明記されていない外に出る操作、提示していない Binding Decision の変更は承認されません。

両立しない案を同時には承認できないため、エージェントは両立する内容をまとめた計画案を示すか、未解決の部分を保留します。個別の選択は人間が求めたときに使い、できるだけ実行環境のチェックリストや複数項目をまとめた画面で一度に送信します。質問を何度も繰り返したり、項目の番号を文章で入力させたりする方法は基本にしません。

作業を許可するのは現在の報告とスコープを承認する実際の送信回答だけです。詳細や修正の依頼、キャンセル、画面を閉じる操作、未回答、時間切れは承認になりません。

完了した作業や読み取り専用の作業結果を伝える報告は、それ自体への承認を求めません。次の作業に人間の判断が必要な場合は、その作業を示して選択を求めます。選択しても、その作業の人間のゲートが免除されるわけではありません。

承認用の質問画面を使えるかどうかはホストとモードによって異なります。使えない場合や承認への利用が認められていない場合、エージェントは制約を説明して停止し、自動的に文字入力の選択肢へ置き換えません。質問の受け付け通知も人間の回答ではありません。

## 柔軟に

DDL は厳格な手順ではありません。

- 望むなら Draft を飛ばして Realize に直行しても構いません
- それでうまくいくなら、ドキュメントを書く前にコードを仕上げても構いません

作業が流れているときは、流れるに任せてください。

大事なのは作業のあとにドキュメントを更新すること（Reflect）です。

## アンチパターン

| パターン                      | 問題                          |
|------------------------------|----------------------------------|
| ドキュメントなしでコードを書く | 次のセッションが設計なしで始まる |
| プロセスに厳格に従う | DDL は厳格な手順ではない |
| LLM に全部やらせる | 人間の判断と長期の視点が欠ける |
| 人間が全部やる | LLM の言語化と技術知識が使われない |
| ツール化を目的にする | 意図が先で、ツールは手段 |
| DDL のドキュメントを永続させようとする | 不要になったら削除する |
| 形式に囚われる | DDL は一時的なメモ |
| エージェントにスタックを黙って選ばせる | 誰も合意していない決定がコードを拘束する |
| ハーネスの記憶を設計として扱う | エージェントは覚えているが、人間は合意していない |
| Direction を契約として扱う | 見通しが固まって誰も見直さない計画になる |
| 要約から承認する | コンパクション（会話の圧縮）を経た会話は報告ではない。人間は目の前にあるものを承認する |

## まとめ

DDL は一時的なメモを使い、人間と LLM がセッション、エージェント、ハーネスをまたいで目的と設計を共有し続けることを支えます。実装から学んだことに合わせ、ループも柔軟に進めます。

最終的にはコードが正（source of truth）になります。DDL のドキュメントは不要になったら削除してください。

Gitに記録・送信する前には、最終差分、正確なメッセージ、送信先を確認します。同時に判断できる一式は、標準の選択画面で1回にまとめて承認します。STOPの待機が解除されていても、`hook` は通常のcommit・pushをその確認案と照合します。実装前の承認や通常の返答だけでは通らず、内容が変われば再確認します。対象は `hook` が受け取る呼び出しであり、実行環境の制約は別に記録します。

**ツール支援の選択肢:** [Claude Code](../../claude-code/) (`/draft`, `/realize`, `/reflect` + サポートコマンド) | [OpenAI Codex](../../codex/) (`$draft`, `$realize`, `$reflect` + サポートスキル)
